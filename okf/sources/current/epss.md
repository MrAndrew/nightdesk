# Summary

FIRST's Exploit Prediction Scoring System gives every published CVE a probability (0-1) of exploitation activity in the next 30 days and a percentile (the share of scored CVEs with the same score or lower). Night Desk shows it next to CVSS and KEV wherever a CVE appears.

# Data rules

* **Validation.** The header must carry `model_version` and `score_date`, and its day must match the dated file the server redirected to; columns must be `cve,epss,percentile`. Rows with a malformed CVE id, a value outside 0..1, a short row or a repeated CVE are rejected (counted). A file with fewer than 90% of the CVEs already loaded (or, on a first load, fewer than 100,000) fails the run as a partial download: the list is not windowed, so a truncated file would otherwise drop scores and record most CVEs as removed. If FIRST genuinely drops more than 10% of its CVEs, every run fails with that message; to accept the smaller file, restart the app once with `OSINTHUB_EPSS_ALLOW_SHRINK=1` set, let EPSS run, then restart without it.
* **Times.** `score_date` from the header (UTC). An older file than the one loaded never overwrites the table.
* **Units.** `epss` and `percentile` are stored as 0-1; the UI shows percentages with one decimal at 10% and above, two below (same on server and client).
* **Atomicity.** The `epss` table is replaced last (`Source.commit()`), only after the lake delta, the record hashes and the run's bookkeeping succeeded. The "already loaded" check reads that table, so a run that fails anywhere leaves the old table and the next run reloads the day for real; the lake delta is written once (record hashes move only with a successful lake write).

# Storage design

About 402,000 CVEs a day. Measured on two consecutive real files (2026-11-08 and -09): the percentile changed for 389,647 CVEs (97%), because it is a rank and every new CVE shifts it, while the probability changed for only 3,216 and 243 CVEs were new. So:

| Where | What | Size |
|---|---|---|
| `epss` table (DuckDB) | Latest score of every CVE: `cve, epss, percentile, score_date, model_version, since` (when the probability last changed), `prev_epss` (the probability before that). Replaced by each new file, sorted by CVE. Answers "latest score" for **any** CVE the app shows. | ~400k rows; DuckDB grew 5.8 MB with it and the 402k record hashes (measured), then flat |
| Lake records | One record per CVE `{"epss": p}` stored only when the probability changes or the CVE is new, plus a `#meta` record (model, score date). The percentile is left out: it moves daily for almost every CVE and is recomputable from the replayed probabilities. A model change rewrites every CVE once (a real change). | first load 2.2 MB; then ~3,500 records = 21 KB a day |
| `events` | **None.** An EPSS score is enrichment of a CVE, not something that happened to it. It never counts as activity: no events, so nothing in event totals, the timeline, the Cinema ticker, Sources "last 24h" figures, entity mentions, sources, last seen or trends, and no severity ranking next to KEV/NVD rows. Every view joins the `epss` table instead. | 0 |

Estimated growth: lake ~0.02 MB/day (≈8 MB a year after the 2.2 MB first load); DuckDB ~6 MB once, then flat apart from new CVEs. The Sources page shows the table's row count as the source's total.

An earlier build made one `epss` event per app CVE. `purge_epss_events()` (at startup and before every EPSS load) deletes such events, their entity mentions and link marks, and resets the affected CVE entities' first/last seen from their remaining mentions, so neither the linker nor a re-link can pick them up; the linker also ignores source `epss`.

Trade-off: the lake cannot reproduce a past day's exact percentile, only the probabilities.

# Where it shows

* `/api/news/cves`: `epss`, `epss_percentile`, `epss_date`, `epss_since`, `epss_prev`, `epss_status` (`ok`, `not scored`, `not loaded`); `POST /api/news/epss` for thousands of ids at once.
* Exploited Vulns and New CVEs panels: an EPSS tag on every row (colour at 1%, 10%, 50%; arrow when it moved by half since the last change), an "EPSS ≥ 10%" chip and an EPSS sort.
* CVE entity side panel: EPSS tile, "Why this matters now" line, patch advice (patch ahead of the cycle at ≥ 10%), patch lists sorted KEV, then EPSS, then CVSS. Full CVE entity page: a formatted EPSS fact (percent, percentile, previous value and date, score date) and the CISA advisories list; raw EPSS attributes are not shown.
* CVE hover cards: KEV, CVSS, EPSS and the newest CISA advisory as tags (mention/claim/source counts are the entity's own, with no EPSS in them).
* Story and article CVE chips ("EPSS n/a" for ids EPSS does not score), global search CVE results, the event drawer for KEV/NVD/advisory events, Explorer (`epss` table, example "KEV by EPSS").

# Corroboration

Ranks NVD and KEV CVEs; a KEV CVE with a low EPSS is still exploited (KEV wins in sorting and advice).
